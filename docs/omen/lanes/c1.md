# c1 — the march opt-in

The emitted C builds `-std=c11 -O3` with no `-march`: baseline x86-64, no
AVX. This lane adds the opt-in and nothing else. The one edited file is
`bend2/main.ts` (`cli_build`, +6/−2); `comp.ts` and `bend.ts` are untouched,
so C2b's load-widening work merges without conflict. No cap moved:
`main.ts` sits at 7257 / 10000 ttok, and `bun gates/repo.ts` passes 56 / 56.

## Spelling

    BEND_MARCH=native bend prog.bend -o prog   # cc gets -march=native
    BEND_MARCH=znver4 bend prog.bend -o prog   # any cpu clang accepts
    bend prog.bend -o prog                     # unset or empty: as before

It's an environment variable because that's how main.ts already takes build
knobs (`CC`, `CUDA_HOME`, `BEND_NO_TELEMETRY`), and it needs no CLI parsing.
The value goes to clang as-is. It lands right after `-O3` in the CPU args,
which the GPU build reuses, so a `!` program's host side gets it too.

## Default is unchanged

A clang wrapper logged the argv of all three bench builds, once with HEAD's
main.ts and once with this one. After removing the temp path the two logs
are identical:

    -std=c11 -O3  -lpthread -lm -o …/gemv      (same for split, blocked)

With `BEND_MARCH=native` the only change is ` -march=native` after `-O3`.
`BEND_MARCH=` (empty) gives the default argv.

The binaries themselves can't be compared byte for byte. Two builds with
the *same* main.ts differ by one byte, because the random `bend-XXXXXX`
temp dir of the emitted `.c` ends up in the binary. So identical argv is
the receipt for the default path.

## Bench — `bash demos/tensor/bench.sh`

Ryzen 7 7700X (16 threads), clang 21.1.7, load average 4–5. The runs are
interleaved default / flag / default / flag, and each cell is the median of
three. The C column is `twin.c`, which bench.sh builds without `-march`
both times.

| bench | C | 1T default | 16T default | 1T native | 16T native |
|---|---|---|---|---|---|
| gemv    | 0.151 / 0.150 | 0.156 / 0.156 | 0.156 / 0.157 | 0.158 / 0.154 | 0.157 / 0.155 |
| split   | 0.150 / 0.150 | 0.154 / 0.156 | 0.153 / 0.157 | 0.155 / 0.153 | 0.157 / 0.153 |
| blocked | 0.041 / 0.040 | 0.108 / 0.105 | 0.105 / 0.103 | **0.086 / 0.079** | **0.078 / 0.078** |

- **blocked**: 1T drops from ~0.106 to ~0.082 s (−23% time, ×1.29), and 16T
  from ~0.104 to 0.078 s (−25%). This matches the C1 figure of ~+25%.
- **gemv / split**: no change (within ±3%), also as C1 predicted. The serial
  shape has no vector work for `-march` to widen.
- A baseline run taken before the edit (0.160 / 0.158 / 0.105 for the
  1T column) agrees with both default runs within ±3%.

## Results don't change

bench.sh fails a row unless C, 1T and 16T print the same four lines, and
every row above passed in both modes. The lines, checked directly:

    gemv    1993981018 3355443199 1073741824 0   (C, def 1T/16T, native 1T/16T)
    split   1993981018 3355443199 1073741824 0   (same five)
    blocked 1297551341 3355443199 1073741824 0   (same five)

`contract(off)` is what keeps these fixed. The emitted C carries
`#pragma clang fp contract(off)` (comp.ts), so `-march` can pick wider
vectors but can't fuse a multiply-add into an FMA. The twin shows what
happens without it: `twin.c` built with `-march=native` prints
`716034538` for blocked instead of `1297551341`, because clang fuses to
FMA. With `-ffp-contract=off` added it prints the right checksum again.
Bend's output didn't move under the flag.

## Portability

`-march=native` builds for the machine that compiles. The binary may use
AVX2, AVX-512 or FMA units that another x86-64 machine lacks, and on that
machine it dies with SIGILL. That's why the flag is opt-in and the default
stays baseline, so a shipped binary still runs everywhere. Use the flag
for benches and local runs on the build host, or name a real target
(`BEND_MARCH=x86-64-v3`) when the binary will run elsewhere. On Apple
silicon clang wants `-mcpu`, not `-march`, for CPU tuning, and some Apple
clang versions reject `-march=native` outright. This lane only measured
Linux x86-64, so the Mac spelling is untested.
