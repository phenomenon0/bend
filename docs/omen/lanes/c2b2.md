# c2b2 — the group guard: `Array.get4`

Outcome: **road 1 shipped.** A new base primitive, `Array.get4(T, a, i)`, reads
slots `i..i+3`, each index wrapped exactly as `Array.get` wraps it. Its native C
states the range check **once for the group**: `if (m - (i & m) >= 3)`, then it
reads four adjacent words, else it reads four wrapped scalars. The blocked
bench's step uses two `get4`s (`a[p..p+3]`, `x[q..q+3]`) in place of eight
`Array.get`s. On the blocked row, 1T/C goes from **2.53–2.57x to 1.06x**
(0.103s to 0.043s, with C at 0.040s). gemv and split move by at most 1.3%.
Every row's checksum and probes are byte-identical across C, 1T and 16T, and
the same as at tip. Road 2 (an emitter pass) was not attempted, because road 1
held.

Road 1 still needed `bend2/comp.ts`. A `get4` written only in base.bend would
compile to four masked `blk_at` gets, which is exactly c2b's blocker. So base
holds the reference definition (the interpreter and the checker use it), and
comp.ts adds the native: the C emission in `arr_op`, a JS runtime helper, and
the intrinsic-table row. `bend2/bend.ts` is untouched.

**Caps are over, in both places, and I did not move them** (§6).

## 1. The change

- `bend2/base.bend`: `Array.get4` and four helpers (`.a`–`.d`), defined as four
  `Array.get`s at `i`, `i+1`, `i+2`, `i+3` (U32 add, so `i+k` itself wraps at
  2^32, then the mask wraps it into the block). The return type is
  `Array<T> & (T & (T & (T & T)))`.
- `bend2/comp.ts`:
  - `arr_op` case `array_get4` emits one range check and two branches. The
    in-range branch reads at `((j + k) << lgs) + n`, where `j = i & m`. The
    fallback branch reads at `blk_at(a, i + k, lgs) + n`, the same expression
    `Array.get` uses. It handles all three cell shapes: `w32` BUF, multi-word
    ARR, and boxed (through `blk_keep`, as `get` does).
  - The result layout is the nested tuple built with `lay_pack`, and it dies
    loudly if that tuple would pass `WIDE`.
  - JS gets `array_get4(a, i)`: `a[(i + k) % a.length]`. That is exact, because
    the length divides 2^32.
  - `array_get4` joins the ops that heat a boxed element type.
- `demos/tensor/bench_blocked.bend`: `dot4.step` becomes
  `q4.a`/`q4.fin` over two `Array.get4`s. The arithmetic and its order are
  unchanged (`s_k + a_k * b_k`, lane k into `s_k`).
- `tests/run/array_get4_wrap.bend`: the wrap-case test (§2).

Emitted C for one `get4` (bench, F32):

```c
u32 at_0 = (u32)((1ull << (blk_cls(st_5) - 0)) - 1);
u32 at_1 = p_1 & at_0;
...
if (at_0 - at_1 >= 3) {
  x_0 = blk_read(e.mem, 0, term_loc(st_5), ((at_1 + 0) << 0) + 0);
  ...                                        /* +1, +2, +3 */
}
else {
  x_0 = blk_read(e.mem, 0, term_loc(st_5), blk_at(st_5, p_1 + 0, 0) + 0);
  ...
}
```

`m - j >= 3` cannot underflow (`j <= m`) or overflow. For blocks of 1 or 2
slots (`m < 3`) it is always false, so those always take the wrapped path.

## 2. Wrap-case receipt (semantics)

`tests/run/array_get4_wrap.bend` prints each group twice: once from `Array.get4`
and once from four separate `Array.get`s. The groups:

- 8 U32 slots, `i = 0..11`: `i = 5, 6, 7` cross the block end, and `8..11` are
  wholly out of range.
- `i = 4294967293..4294967295`: `i+k` wraps at 2^32 before the mask.
- 2 slots, `i = 0..2`, and 1 slot, `i = 7, 8`: `m < 3`, so every group wraps.
- A two-word record `P{a, b}` (`lgs = 1`) at `i = 0` and `i = 2` (crossing).
- Boxed `String`s at `i = 0` and `i = 3` (crossing), which exercises the
  `blk_keep` path.

## 3. Mechanism and asm (before → after)

The in-range branch reads `base + j + k` for `k = 0..3`, which SCEV sees as
consecutive, so SLP packs the four loads into one `movups`. Here clang goes
further: `p` advances by 4 from a multiple of 4, so it proves `m - (p & m) >= 3`
and deletes the branch. What remains is **one** `and` per group, then a packed
load.

Tip, the hot loop (one `and` + one `movss` per element, stitched with
`unpcklps`):

```asm
lea    (%rdi,%r8,1),%r11d
inc    %r11d
and    %eax,%r11d          ; mask, per element
...                        ; 8 masks per step
movss  (%rcx,%r10,4),%xmm2
movss  (%rcx,%rbp,4),%xmm3
unpcklps %xmm2,%xmm3
movss  (%rcx,%rdx,4),%xmm2
movss  (%rcx,%r9,4),%xmm4
unpcklps %xmm2,%xmm4
mulps  %xmm3,%xmm4
addps  %xmm4,%xmm0
```

After, the same loop (unrolled ×2 by clang; one mask per group of four):

```asm
lea    0x100000(%r8),%r9d
lea    (%rdi,%r8,1),%r11d
and    %eax,%r11d
and    %eax,%r9d
movups (%rcx,%r11,4),%xmm2
movups (%rcx,%r9,4),%xmm3
mulps  %xmm2,%xmm3
movaps %xmm3,%xmm2
shufps $0xe2,%xmm3,%xmm2
addps  %xmm1,%xmm2
shufps $0xe7,%xmm3,%xmm3
addps  %xmm0,%xmm3
```

Counts over the whole object (`clang -O3 -c`, `objdump -d`):

| | `movups`/`movaps` | `movss` | `unpcklps` | loop-vectorize "cannot identify array bounds" |
|---|---|---|---|---|
| tip | 283 | 3332 | 1024 | 256 |
| after | 1819 | 1284 | 0 | 256 |

The loop-vectorize remark count is unchanged. That is expected: the widening
is SLP inside one iteration, and the loop vectorizer still cannot vectorize
across the strict-FP accumulator chain. (c2b's "299 packed moves" used a
broader pattern; the numbers above are this report's own.)

## 5. Residual

Blocked sits at **1.06x** (0.043s vs 0.040s), which is under the ≤1.15x bar.
I did not attribute the last 0.003s. The after-loop keeps four scalar
accumulators and SLP maps them to two xmm halves joined by `shufps`, where
C's twin keeps one packed accumulator. That is a plausible cause, but I did
not measure it.
